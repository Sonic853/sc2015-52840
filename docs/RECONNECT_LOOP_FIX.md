## 2. 已复现：保留RX不等于确认相位已认证

### 双端静态依据

原版接收器`d0ggle.bin` SHA-256为`93112caa267e5d79cd8bc26acfd6cda5a1a6b5a682ab7594b262dde510edba21`。证据为工作区既有正确8051/Thumb架构的独立Ghidra导出，非REA Evidence、非运行抓包。

- 接收器`D:1cf8..1e78`准备偶/奇两个下行缓存，`D:2324..2366`根据已认证上行的bit2相位退休缓存。新缓存安装会清除该缓存所需的旧相位见证。
- `D:221e..222f`选择预装ACK，`D:22e7..2304`对重复包认证后仍更新相位；认证失败不会进入相位更新。
- 手柄`P:0ec4..0f1c`只尝试下一个下行counter，并在解密失败时恢复counter。
- **`P:2c7a..2cb6`只对单字节反馈ACK，或成功认证的新下行载荷，调用`P:1194`处理上行序号回显。** 旧载荷认证失败时，即使header中的上行回显看似正确，也不能让发送队列前进。
- 原版看门狗由新序列认证刷新到41，每8hop递减一次；重复认证只更新相位、不刷新看门狗。当前该规则及按RX记录hop推进的时序与原版相符。

原版在RF处理路径执行认证，并有nRF24硬件ACK FIFO流水。XIAO在ISR从已发布快照直接回复，认证稍后由loop执行；这扩大了“手柄已推进、接收器尚未认证”的窗口。普通lane选择、清相位公式本身没有翻译错误。

### 失败回归

新增软件模型保留生产Receiver、CCM、快照和接收队列边界，并按上述手柄分支处理反馈：

1. 接收器已认证上行counter2；新安装的下行counter1/2清掉其相位见证，第三条下行等待。
2. 一份此前发出的counter1旧上行到达。它被保留，且有旧counter下的合法MIC，但接收器当前向前窗口不能认证它。
3. 旧ISR策略仍可让手柄先收到下行1；loop认证失败，因此没有保存该次相位。
4. 手柄接收下行2后相位绕回，接收器仍保留下行1，第三条无法安装。手柄拒绝旧密文，也不处理其中的上行回显。
5. 上行停在同一counter反复重传，最终原有看门狗断开。模型出现超过300次重复认证，RX环未满。

修复前要求连接持续的回归失败；旧策略对照明确停在下行2并断开。该模型证明软件路径存在，**不证明现场323次MIC失败都由此种旧包顺序造成**。

### 修复

发布普通业务ACK时，只有该lane安装后已经收到所需相位的**认证成功**上行，才允许发送其载荷：

```text
lane = 1 - peer_parity
载荷可用 = lane.valid && (phases & (4 << lane))
否则：单字节反馈ACK，回显最近已认证的上行序号
```

这样即使当前RX稍后认证失败，发送载荷所需的相位见证也已存在。尚无见证时仍正常回应反馈ACK，等loop认证并发布后继续，可能增加一次poll；ISR不执行AES。

发现/join及已认证换钥请求的bootstrap重发分支保持其独立规则。CCM/nonce、lane退休公式、看门狗阈值和物理ACK时序未调整。

## 3. 已修正：旧USB命令误作用于新会话

旧USB环只记录slot。B2作为第17条命令进入环时，第一轮只处理16条；中间若该槽恢复接入，下一轮旧B2会断开新会话。普通设置被RF满阻塞时也可跨越同样的槽复用边界。

原版B2在`D:1aa9→453e`检查当时是否已连接；离线调用不留一个能命中未来会话的请求。XIAO异步分离需要显式保留这一目标边界。

修订号10为每槽引入递增session generation，在实际reset/join边界更新：

- 转发无线命令、B2、B3在SET DATA接受时捕获generation，而不是等ACK回调才读取。
- 查询去重也包含generation，避免复用上一会话的就绪状态。
- loop先判定generation，旧命令计数并退休，不再等待RF容量，也不作用于新会话。
- 本地身份、诊断、熵提示等命令仍按其本地作用域处理；当前会话B2继续正常断开。

回归覆盖离线B2/B3/设置排队后接入、RF满时旧命令跨重连、DATA→ACK之间换会话、以及有效B2。现场旧FA未记录B2历史，因此此修复不等于已确认本次运行发生过旧B2误伤。

## 4. FB v1：实际断开原因与传输状态

修订号>=10支持本地`fb 00`，零Report ID单独传入；回复64字节：

|偏移|内容|
|---|---|
|0..3|FB、62、版本1、固件修订号|
|4..23|五个LE32断开计数：看门狗、主机B2、同ID新会话替换、bootstrap加密失败、清除绑定|
|24..27|LE32 `ack_deferred`：有载荷但等待认证相位，实际发送单字节反馈ACK的次数|
|28..31|LE32 `stale_session_sets`：已退休的旧会话USB SET数|
|32..59|四槽各7字节，见下|
|60|当前连接mask|
|61..62|保留0|
|63|重复固件修订号|

每槽7字节：最近断开reason、watchdog、待发RF片数、lane/phase flags、RX counter低8位、TX counter低8位、保留0。flags bit0/1为lane0/1有效，bit2/3为协议相位见证。reason为0无、1看门狗、2主机B2、3新会话替换、4加密失败、5清除绑定。

在线时显示实时传输状态；离线时保留最终断开前快照。最近reason在重连后保留，离线B2/B4不增加实际断开计数。计数低8位会回卷，不能当完整39位序号。FB不包含key、IV、绑定ID或命令参数。

网页新增`transportLink`及“无线会话”面板；CLI新增`transport_link`。新版网页仍只对老固件使用其支持的诊断命令。`ack_deferred`增长本身是门控工作，不是发射失败。

## 6. 实物复测

1. 保留绑定升级，刷新网页并确认当前修订号11和FB“无线会话”面板，然后断开网页。
2. 重启Steam，普通Steam键恢复，连续操作/滑动左右板至少2分钟，记录有无断连和触觉失效。
3. 若失败，保持接收器供电，记录本地时间并保存Steam日志；退出Steam后导出诊断JSON，确保包含`transportLink`。
4. 看门狗计数增长时结合离线slot的lane/phase/RX/TX快照；若主机B2或会话替换计数增长，则沿对应入口定位。无需靠反复清库来区分这些原因。
