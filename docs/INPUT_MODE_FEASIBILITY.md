# 输入模式、RESET与手柄开机组合键：可行性分析

日期：2026-11-03。对象为当前SC2015接收器修订号11，参考本地 `D:\Git\openpuck\openpuck` 的 `0114623`。本文是设计与静态分析，未实现输入模式切换，未为这次分析刷机或操作手柄开机。

## 结论

1. **接收器可以增加Xbox/XInput、Switch、PC DualSense等USB输出模式。** 保持SC2015无线协议，在已经解码的输入和USB输出之间增加转换层；不是移植SC2射频驱动。
2. **单击RESET后重启并切换模式有可行路径**，但需验证工厂bootloader留下的复位原因，尤其双击UF2/刷写退出。当前没有判定RESET不可用，也未证明该板上所有边界可靠。
3. **仅修改接收器，不能直接在官方手柄的开机选择函数里注册新组合键。** 已核对函数是手柄主控中的固定条件分支，发生在无线连接建立前；未建立官方可写开机组合表的协议依据。
4. **可在接收器注册“连接后的组合键”。** 如果用户从开机一直保持候选按键到第一份有效输入抵达，就能获得近似“组合键开机选择模式”的体验；它本质仍是连接后识别，不能捕获此前已松开的键。
5. **不应把Steam+A/B/X/Y直接改为四种USB模式。** BLE版中它们已有接收器/BLE连接与配对用途，附加背键并不会绕过现有分支。

## 1. OpenPuck实际怎样切换

源码证据：

- `OpenPuck/controllers.cpp:18`按 `g_usbMode` 选择不同USB控制器实现。
- `OpenPuck/rf_link.cpp:3882–3941`在已解码的SC2输入中检测四背键+面键/方向键，按槽去抖后调用 `modeSwitchReboot()`。
- `OpenPuck/OpenPuck.ino:112–121`保存模式、USB detach、等待60ms、标记主动重启，再执行 `NVIC_SystemReset()`。
- `OpenPuck/config.cpp:173–290`实现保存模式与一次性bootMode；这是接收器自己的配置，不是向手柄注册开机键。
- `OpenPuck/fault_diag.cpp:443–490`读取复位原因用于诊断，并未将板载RESET单击做成模式轮换。

该分支部分说明已落后于代码，例如当前 `mode_xinput.h` 明确为静态单Xbox 360控制器，不能沿旧架构图推断为四个XInput设备。SC2015只有两个背键，也不能原样采用SC2的四背键组合。

## 2. USB模拟模式的可行范围

|目标|判断|需要补充的部分|
|---|---|---|
|PC Xbox/XInput|可实现，适合优先做|专用USB class driver、20字节输入、rumble输出及中性状态；不是只修改VID/PID|
|Switch HORIPAD|较简单的输入路径|HID描述符、8字节输入、按键/摇杆映射；该参考模式没有陀螺仪和震动|
|Switch Pro|可实现，工作量较大|USB握手、0x21子命令回复、0x30报告、校准/SPI模拟、IMU与震动转换；实际Switch仍需验证|
|DualSense/PS5格式用于PC|可实现|054C:0CE6身份、输入及Feature报告、触摸/IMU坐标单位、主机输出处理|
|真正PS5主机|当前没有兼容依据|OpenPuck将该模式标作PC only，不能把HID模拟等价为PS5主机认证与完整兼容|
|Xbox主机|必须区分代际|参考分支有Xbox 360软件认证及PC测试，但文档保留实际主机失败/未验证；不能扩展为Xbox One/Series支持|

当前固件Flash95192字节、全局RAM30124字节，资源上有增加转换层的余量；这不证明新增USB端点、实时调度或所有主机兼容性已满足。

具体改动点：

- `protocol.cpp:773–819`已将认证输入重构为42字节状态并通过 `hooks_.input`输出，可作为统一输入层入口。
- `usb.cpp:375–405`目前固定Valve五HID布局，需要按模式创建不同描述符及回调。
- `usb.cpp:873–969`有Steam特定EP0包装，并强制device class/subclass/protocol为0、移除序列号、拒绝vendor control请求；这些必须按模式分派，否则会破坏XInput等身份/控制流程。
- `tools/build.py`的二进制审计目前针对原版HID布局，需要增加模式相关检查。
- 模式配置应在USB最终attach前加载；当前setup先 `usb::begin()`、后读绑定，启动顺序需调整。
- SC2015只有一个物理摇杆、两个背键，右摇杆需由右触控板等输入映射；Switch的数字扳机、PS触摸坐标、陀螺仪单位要独立转换。
- 模拟模式不能依赖Steam代为初始化手柄；需要2015版的输入/IMU/键鼠模式配置。OpenPuck的SC2初始化及0x80触觉链路不能照搬。2015版0x8F转换还应遵守现有有界队列策略。

USB模式是整只接收器的身份；多手柄的选择/映射需要另定规则。可先验证一个虚拟手柄，再扩展多槽。

## 3. 板载RESET单击

当前XIAO variant将 `PIN_BUTTON1`定义为不可用的 `PINS_COUNT`；固件使用的D0是P0.02外接配对按钮，长按500ms进入配对。它与板载RESET不是一个输入。

RESET触发MCU复位，应用不能先收到普通GPIO点击事件再执行切换。可采用：

```text
按RESET → MCU复位 → bootloader → 应用读取复位原因
        → 确认是应当切换的按键复位 → 选择/保存下一模式
        → 构建对应USB身份 → 重建无线会话
```

Seeed核心1.1.13 `cores/nRF5/wiring.c:35–40` 在 `init()`中锁存并清除 `NRF_POWER->RESETREAS`，应用应调用 `readResetReason()`（72–75行），不能到setup里才直接读取已清零的寄存器。

上游 [Adafruit bootloader0.6.1 main.c](https://raw.githubusercontent.com/adafruit/Adafruit_nRF52_Bootloader/0.6.1/src/main.c)使用 `0x20007f7c`标记和500ms双击窗口。此前本板INFO声明0.6.1/S1407.3.0，但没有证明厂商镜像与上游逐字节一致。

实现前应先记录：冷上电、单击RESET、双击进UF2后返回、刷入后返回、软件重启和watchdog的启动原因。只在可靠识别的用户单击路径轮换；USB bus reset不是MCU按键复位，不应切模式。特别要核对DFU退出的残留RESETPIN，不能假设所有带该位的启动都是新单击。

不建议为此将RESET改成普通GPIO。模式状态宜使用独立可靠配置，避免每次切换都重写绑定库；新增Flash区域必须纳入链接和UF2保护。GPREGRET已用于F9/DFU，GPREGRET2或`.noinit`跨工厂bootloader是否保留也必须验证。

## 4. 手柄开机组合键由谁处理

```text
手柄Steam键唤醒/上电
  → LPC11U37主控启动、采样按键、选择私有接收器或BLE模式
  → 配置/启动nRF51无线链路
  → 对XIAO发现/恢复认证、建立会话
  → 发送普通输入（包括仍按下的按键）
  → XIAO重构状态并决定如何输出USB
```

因此，XIAO在连接建立前无法看到手柄GPIO，也无法阻止其先进入BLE。进入BLE后，本工程的私有2.4GHz接收链路不会收到它的普通输入。

已恢复的发现/join载荷也不含可直接使用的“开机组合键编号”：发现为 `00|id8`；join明文为 `address5|id8|material4`。依据工作区 `analysis/receiver_d0ggle/IMPLEMENTATION_LINK.md:61–150`；不将这些随机材料解释为按键状态。

### 4.1 本地BLE host镜像的固定选择函数

目标 `vcf_wired_controller_d0g_5b0f21bd.bin`，SHA-256：

```text
2c42adb211c9f209dae5ac223ed451229d0aa08b139acfbd56f36b0d8add6fc4
```

已核对的调用关系：`main 0xf164 → init 0x60d0 → selector 0x64b4`，main随后才调用radio-link start `0xd560`。以下为本地镜像的静态选择，不是本轮手柄操作实测：

|保持Steam开机时的附加键|选择函数动作|对应模式解释|
|---|---|---|
|无|沿用保存的transport值|普通恢复；上次是BLE时不能假定它会连XIAO|
|X|transport=2，动作=2|私有接收器配对|
|Back（左前小键）|transport=2，动作=1|私有接收器选择/切换分支|
|A|transport=2，动作=0|私有接收器普通恢复|
|B|transport=3，动作=0|BLE普通恢复|
|Y|transport=3，动作=2|BLE配对|
|Start（右前小键）|更新0/1连接索引，transport=3，动作=1|BLE连接目标选择分支|

Steam索引10控制采样循环；按键判断优先级是 **X → Back → A → B → Y → Start**。它逐个检查按下状态，并不要求其他键全部松开。所以 `双背键+X+Steam`仍命中X的配对分支，不能靠额外修饰键覆盖它。

汇编直接传入的按键索引为4、11、5、3、2、9、10。循环最多检查100轮，延迟helper参数为5；约半秒是静态估计，不作为实测按键窗口承诺。退出时更新保存的transport值，相关写入函数为 `0x6c98`（EEPROM偏移0x148），连接索引写入为 `0x6cc8`（0x149）。这是保存已选模式，不是保存任意组合键表。

参考官方 [Steam Controller (2015) BLE FAQ](https://help.steampowered.com/en/faqs/view/1796-5FC3-88B3-C85F)及其可索引的X/Y配对说明；本次正文抓取只得到页面外壳，详细表以本地代码分支核对。Back/Start后续目标选择的全部策略、其他固件版本及工厂分支没有穷举。

### 4.2 旧production不能与BLE版混用

旧主控 `vcf_wired_controller_d0g.bin`，SHA-256 `586598f6c4415c2fd03656803d74908929f0aeee76edb289d6a8a38682453b1c`，选择函数 `0x60c8`：检查Steam、X、A，X分支还检查LB并保存一个附加标志。A设动作1，与上述BLE版A设动作0不同。

因此不能因为旧版没有B/Y分支就将它们认定为当前手柄可自由占用的开机键，也不能把LB笼统称为从未使用。已记录的手柄属性曾声明主控build1527718333（0x5b0f21bd），与BLE文件版本名相符；这仍不是读取板上完整固件后的字节同一性证明。

## 5. 能否增加新的开机键

### 真正修改手柄的开机选择

要在无线接入前新增行为，需修改手柄LPC主控的选择/配置逻辑，必要时扩展与radio的命令交界。当前未证实有可由XIAO下发的“注册新开机组合”命令；普通Steam Input按键映射也不能替代此阶段。

本地OpenSteamController的自定义NinSwitch是直接USB输出，既有分析没有恢复出其官方式无线启动链，不能将它当作保留现有无线能力的开机热键补丁。

### 只改XIAO：连接后识别仍保持的键

这是更实际的方案。BLE选择函数没有检查两个背键（索引20/21）；其输入组装函数 `0x8608`将它们分别放入按钮位 `0x8000`、`0x10000`，普通输入有接收器可观察的字段。

**范围限定**：未在该选择函数中使用，不等于穷举证明所有bootloader、工厂模式和运行时设置都不使用它们。仍需实际捕获候选键开机后的第一批输入，验证没有被吞掉或造成其他模式变化。

候选交互：

- 简单开机选择候选：`左背+Steam`、`右背+Steam`、`双背+Steam`，背键一直保持到连接和反馈。应先确认上次transport为私有接收器，否则先用A+Steam恢复；Steam键可在唤醒后松开。
- 若需要四个直接目标，可研究“双背键+摇杆四方向”作为选择器，保持到连接后；它是设计候选，轴数据首次可用性和未占用情况仍需测量。
- **更可靠的首版交互**：先普通开机连接，松开Steam，再用 `双背+A/X/Y/B`分别选择Steam/XInput/Switch/DualSense(PC)。这里的A/B/X/Y发生在连接之后，不与官方开机选择抢优先级。具体映射为建议，不是当前固件功能。

识别点应放在认证、解压之后、USB映射/桌面输出之前。建议以时间和新鲜输入去抖，匹配目标模式后只执行一次；释放后才允许再次触发；目标已经是当前模式时不重启；切换组合不送进游戏或桌面。采用直接目标选择，比每次自动循环更容易避免重连后仍持键造成连续切换。

可在XIAO自己的配置中保存这套组合规则，这才是接收器侧的“注册”。它不能改变手柄原有的开机扫描逻辑。

### “连接窗口”不能严格等同于“刚开机”

本工程会话generation能区分旧会话，但当前已恢复的join没有手柄开机原因。手柄冷开机、RF掉线重连和接收器重启都可能表现为新会话；仅在join后开放2秒并不能完全防误触。若要求只在真正冷开机生效，需要额外手柄侧依据；否则应明确设计为一次性连接窗口或运行时长按快捷键。

模拟模式切换仍需USB detach/重新枚举。首版可沿用保存目标→重启的策略，会重建无线会话；纯USB重配而保留RF需要另外解决TinyUSB对象、接口映射和待发传输生命周期，不是已有保证。

## 6. 专项：左背键+Steam开机能否切换接收器模式

**结论：有明确实现路径，只需给接收器增加识别逻辑；条件是仍走私有无线，并将相关键保持到接收器看见有效输入。** 尚未实测该组合在用户手柄上的首包行为，当前修订号11也未实现切换。

### 静态依据

1. BLE开机选择 `0x64b4`不查询左背索引20，所以在本次已核对路径中，它不会覆盖普通Steam启动所选的transport。
2. 同一镜像输入组装 `0x8608`把Steam索引10映射为 `0x2000`，左背索引20映射为 `0x8000`。两者同时上报时可检查 `0xa000`，不能只查Steam或CRC正确。
3. 当前 `Receiver::receive()`先做CCM认证，拒绝MIC失败，并在重复counter时直接返回；新类型0输入才调用 `report()`（`protocol.cpp:593–658`）。
4. `report()`重构状态后放到64字节报告的offset8，调用 `hooks_.input()`，随后还会生成桌面键鼠；因此可以在两个USB输出路径之前消费模式组合。

普通输入报告上的识别条件示意：

```cpp
uint32_t buttons = uint32_t(report[8]) |
                   (uint32_t(report[9]) << 8) |
                   (uint32_t(report[10]) << 16);
bool leftGripAndSteam = (buttons & 0x0000a000u) == 0x0000a000u;
```

这只表示按键条件，尚不包含报告类型、连接窗口、会话、去抖和一次性锁，不能当成完整补丁。

### 用户操作与识别策略

- 按住左背，再按Steam唤醒；保持到连接及切换提示后松开。
- 若要求严格证明“两键同时被看见”，必须等首批有效报告中同时出现Steam和左背，过早松开Steam会无法触发。
- 更宽容的开机体验可在新连接短窗口内允许“左背仍按住、Steam已松开”。但接收器只能证明连接后左背状态，不能证明唤醒瞬间的组合，也更容易误触。两种策略需明确选择，不能混称为同一保证。
- 若手柄上次保存为BLE，左背+Steam仍会选BLE，XIAO收不到；先A+Steam回到私有接收器模式。也可研究左背+A+Steam强制私有模式，再由接收器识别左背，A仍承担官方原有作用。

### 循环切换必须解决的状态

若目标为 `Steam → XInput → Switch → DualSense(PC) → Steam`：

1. 每个新会话只开放有限识别窗口，使用新鲜普通输入去抖；已有手柄正常使用期间按左背不触发。
2. 一次触发后立即锁住，直到有效松键。尤其使用“保存模式→MCU重启”时，必须把抑制重复触发的状态带过这次重启；否则持键重连会不断轮换。
3. 不应仅靠未经验证的GPREGRET2/.noinit保留性。可在可靠模式配置中加入一次性切换标记，并明确松键、掉电和恢复策略；也可以先做固定目标切换，使“已是目标模式”直接成为无操作。
4. 识别回调仅提出请求；当前RF包处理完成后，由loop安排保存、释放旧USB输入、detach及切换。不能在RADIO IRQ或USB回调中直接写Flash/重启。
5. 明确只允许哪个手柄控制全局USB模式；切换按键在判定期间不应泄漏成游戏操作或桌面快捷键。

最小验证是捕获普通开机、左背+Steam持续保持、Steam早松/左背保持及两键都早松的首批输入，记录会话和原始按钮位；同时检查普通RF重连、持续持键跨重启不会误切。此项可先做只记录的诊断，不必先实现全部USB模拟模式。

## 7. 建议实施顺序

1. 先做诊断验证：XIAO启动原因；手柄普通/A+Steam及候选背键开机的首批原始按钮状态。现有F0/FC未提供完整启动原因，不能用目前计数推断RESET可靠性。
2. 建立与USB模式无关的输入和组合键识别层，保留一个固定的“回到Steam”入口；先验证连接后双背组合。
3. 加入独立模式配置和USB模式框架，再实现PC XInput；随后按需求加入Switch Pro、PC DualSense。
4. 单击RESET作为板端备用入口，在复位/DFU边界确认后启用。纯Xbox/PlayStation身份下可能没有当前网页的vendor HID诊断接口，固定返回Steam的手柄组合或板端入口尤其重要。
