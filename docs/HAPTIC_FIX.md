# 修订号7：输入正常，但触控板没有触觉反馈

当前交付为修订号11，包含本页修复、[96熵设置修复](ENTROPY_FIX.md)、[ACK相位/会话隔离修复](RECONNECT_LOOP_FIX.md)及 [队列分账/有界等待](QUEUE_IMPROVEMENTS.md)。本页保留修订号7的根因与回归依据。

## 实物对照与定位

用户按“升级XIAO并配对 → 原版接收器并配对 → XIAO并配对”复测：三次Steam均识别手柄，原版左右触控板滑动有反馈，两次XIAO均无反馈。

`controller_ui.txt`的04:11:08、04:15:22、04:16:49段均读取到同一2015手柄的Type2、ProductID4358、相同序列号、capabilities及主控固件时间，并使用同一份`controller_steamcontroller_gordon.vdf`。结合用户的操作顺序，04:11/04:16的`619329d`实例与04:15的`3a67dbf0`实例可用于这次对照；HID路径本身不是永久物理身份。

`sc2015-diagnostics (4).json`显示修订号6、一个已保存非bootstrap绑定、connectedMask=1、19319次认证上行，RF/USB队列和Flash丢弃均0。FA最近SET为槽0的**143=`0x8f`、实际USB长度64**；最近GET为186=`0xba`、payload长17，是另一次芯片信息查询，不能当作触觉执行确认。网页采样时间是UTC，Steam日志为本地时间，需要先对齐时区。

这确认XIAO的USB回调收到过触觉命令。FA v1不能辨别发送进程，也不保留每次参数或无线发送次数，不能据此证明全部脉冲已发出。522次累计MIC失败、4051次重复上行也不能单独定位此次下行失败；ACK发射完成不等于手柄执行了振动。

## 已复现的软件错误

修订号6的`Receiver::feature()`对所有无线转发命令统一使用`feature_waiting`和`wireless_reply_ready`：

1. 第一次SET排队并设置`feature_waiting=true`。
2. 后续相同`cmd,len,args`直接返回成功，不再排队。
3. `0x8f`脉冲不要求应用层Feature回复；GET一个`8f 00`占位也不消费实际回复，因此相同脉冲可能被无限期抑制。
4. 即使收到写命令回复，已有缓存也可能让下一次相同SET只命中缓存。

这不是FIFO溢出，提前返回不会增加queue_full或command_drops，所以现场“丢弃计数0”不能排除此错误。它足以解释连续滑动缺少持续反馈，但不能仅凭静态分析保证所有实物触觉异常都来自这一处。

原有两项测试误用`0x87`写设置来验证读取去重，掩盖了这一区别。现改用读取命令`0x84`，并独立验证重复写入。

## 原版静态依据

使用工作区既有正确8051架构的独立Ghidra导出，**非REA Evidence、非本轮实物抓包**。原版`d0ggle.bin` SHA-256为`93112caa267e5d79cd8bc26acfd6cda5a1a6b5a682ab7594b262dde510edba21`：

|命令|原版CODE路径|语义|
|---|---|---|
|`82/83/84/89–8c/aa/ab`读取|`1951..19b0`|pending/cached查询不重复排队；在线未就绪时SET忙|
|`8f`触觉|`19ce..19d8 → 1ae3 → 1af2`|连接时每次尝试排队，不比较pending或缓存，不等应用回复|
|`87`等默认写入|`19b1..19cc → 1ae3 → 1af2`|每次尝试排队；该路径检查入队失败|

`1850..186c`从USB参数长度取实际命令总长；`1b1d..1b75`共用27字节type2续片/type3末片。没有触觉专用RF类型、额外Report ID或片号。`8f`原版会在未连接或入队失败时仍本地完成，这也不是“振动执行成功”的确认。

依据文件：工作区`analysis/receiver_d0ggle/dispatch.tsv`、`feature_functions.md`、`assembly.tsv`及`IMPLEMENTATION_LINK.md` §4。手柄radio的`P:1e04..1e92`将type2/3重组后送主控，不能把UART前缀`50`额外加到接收器RF中。

## 修订号7实现与验证

- 仅`featureQuery()`读取命令可以使用pending/回复缓存去重；AE/BA继续采用修订号6的读取兼容扩展。
- 无线写命令每次独立排队，并使旧写回复不能成为下一次SET的缓存命中；不要求虚构应用回复来解除等待。
- 保持原字节、27字节切片、AES/nonce、双lane链路重传和绑定布局。每个USB写入是新操作；同一已序列化RF包的链路重传仍是同一操作。
- FIFO容量仍为12片；超容量由既有queue_full记录。本补丁不提供无限突发吞吐保证。

新增回归先在修订号6生产代码上失败：第二个相同脉冲无法从RF读取；补丁后通过。测试直接驱动生产USB wrapper和协议，再由模拟peer以递增下行counter解密核对：两个板选择值各3次同参数突发、后续无GET脉冲、已有写回复缓存后的相同SET、两个重复64字节设置命令的27+27+10切片，以及12片满队列/第13次拒绝和排空。既有50次读取SET忙去重继续通过。断言数字、构建hash与资源见 [VERIFICATION.md](VERIFICATION.md)。

修订号7当时的USB和RF peer为软件模拟，没有实测触觉强度/时序。后续本机观察见 [修订号10对照](LIVE_USB_COMPARISON.md) 和 [修订号11队列验证](REV11_LIVE_VALIDATION.md)。
