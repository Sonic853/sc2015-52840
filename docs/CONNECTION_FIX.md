# 修订号4：重连与连接矩阵修复

## 现场证据能说明什么

用户已确认修订号3首次配对成功，随后关机重连失败。失败快照为：ACK安排/READY/完成均5098；pipe1收到3806包，最近`H=2,len=22,S1=3`；累计认证1257、MIC失败28，当前四槽均未连接、activePipes=2。

因此此次已越过ACK收发问题，停在恢复绑定接入；1257次认证属于累计值，不能证明这次重连成功。报告没有绑定记录数及首次保存过程，**不能仅凭它确定是未保存、密钥过早保存还是临时选择器失效**。修订号4对三条可复现路径同时处理，并增加不含密钥的F8诊断。

## 1. H=2恢复不再依赖临时H=0选择器

原实现对`H=2`要求`lookup_valid_`，否则直接返回，既不做认证也不增加MIC失败。这意味着已有正确持久绑定，但H=0未处理或缓存被接入清理后，单独重试的H=2仍不能恢复。

修订号4：

- 优先尝试仍与数据库一致的缓存选择器；未知手柄的H=0查询不会清除另一个有效选择器。
- 缓存缺失/不匹配时，最多尝试20条已保存记录。
- 成功必须同时满足 **CCM/MIC正确、接收器地址正确、解密后的手柄id8等于该条绑定id8**，不是随便找到一把能解密的key就接入。
- 不使用未知key、不靠猜测生成key、不把空库当作已绑定。

这是兼容性恢复策略，保持原H=0/H=2和nonce等空口字段。原固件的H=0缓存有一手依据`D:15d1..164f`；这里不声称原厂本身已实现这项fallback。

## 2. 保存最终密钥，区分本地配对和主机配对

旧B3仅检查connected+pending；过早调用可能保存bootstrap key，且随后换钥会清除先前排队的05。新实现接受保存请求，但等待**最终key已安装且收到用该key认证的上行**，再持久化并排`05`。

- 本地模式：空库启动、D0按键启动的配对自动提出保存请求；最终key确认后保存，不依赖网页或Steam继续在线。
- 主机模式：AD开启的配对继续由B3提出保存；网页只发一次B3并轮询完成，不把短暂state3认成失败，也不反复写Flash。
- Flash失败保持pending，停止自动反复重写；用户可重试。
- 最终确认前断开不写bootstrap key，F8记录`unsaved_disconnects`。

修订号3已经落盘但错误/缺失的key无法从密文逆推出；若F8显示空库或旧bootstrap记录，可能需要用X+Steam新配对一次。更新应用不清空其他有效绑定；重新配对相同id只更新该id。

## 3. 连接数量和调度通知

原`D:17ad..17b3 / 2b7a..2b80 → 4106..411c`会给所有槽置count-dirty。当前实现据此补齐：

1. 初始04成功入队。
2. 首次USB连接通知。
3. dirty时排`03,connected_count`，失败保留dirty再试。
4. join/断开均使其他在线槽也得到新count。

没有把接收器1500µs跳频周期乘以连接数；03由手柄消费并参与其发送调度。

## 4. 丢join ACK、快速重启和满槽

- 成功join缓存**这次认证的请求和此前公告的22字节ACK**。同一请求重发不再新建槽、重新随机挑战或重新安装会话。
- IRQ只匹配已认证请求的精确字节以选择缓存ACK，不在IRQ做AES。收到该业务pipe的认证上行后结束重发窗口；超时断开也清除。
- 响应表采用双缓冲：完整生成ACK、重发记录和pipe mask后一次交换，避免不同nonce/分配epoch混用。
- 有空槽时，同id快速重启沿用已公告的新目标pipe，认证通过后退旧槽，保持其他槽在线。
- 四槽满时，最后一个尚未确认join仍有精确重发窗口；四槽均确认后关闭普通接入，快速重启要等待旧会话超时释放，不挤掉其他在线手柄。

这是有限重发窗口，不是无限丢包保证；若所有ACK一直丢失直至会话超时，新配对仍可能需要重新开启。

## 5. 按实际RX时序处理watchdog

原主循环先处理积压RX并刷新watchdog，再扣除全部历史hop，可能立即耗尽刚刷新的会话。

现在每个RX携带本机累计hop序号；主循环先推进到该包的hop，再认证/刷新该会话。队列真正为空时才原子取得当前idle hop并继续推进。Flash暂停后的catch-up、身份导入后的时钟复位也保持一致。hop不是无线报文的新字段。

## 6. 已执行的软件连接矩阵

以下均由生产协议代码、真实响应选择helper及模拟peer执行；**不是新修复版实物通过列表**。

|情况|软件预期/验证|
|---|---|
|空库启动/按键配对，无主机B3|最终key确认后自动保存并发送05，接收器重启后能H=2恢复|
|网页/Steam AD显式配对|主机保留提交控制；不自动覆盖未提交记录|
|B3先于换钥|只暂存请求，不写bootstrap，确认后保存最终key|
|保存前断开|不虚构持久绑定，记录未保存断开|
|普通关机后H=2重连，缺H=0|验证已保存id/key和地址后恢复|
|接收器重启/连续三次恢复|从序列化持久记录恢复，不依赖旧RAM|
|其他已知或未知手柄交错查询|错误缓存不阻断正确绑定恢复|
|绑定位于索引19|最后一个存储位置也能恢复|
|两个H=2用同一个旧challenge准备|只一个消费该公告；另一个用新challenge重同步，不错分同pipe|
|最终join ACK丢失并重发同一包|重发原ACK，不重复占槽或旋转challenge|
|四槽中的最后join尚未确认|保留精确重发窗口；不允许第五个占槽|
|四槽全部确认，同id快速重启|等待旧槽超时，其他三槽保活|
|有空槽，同id快速重启|新会话使用公告pipe，旧会话被清理，其他会话保留|
|join/断开后的03广播|所有在线手柄最终收到正确连接数|
|主循环积压数百hop并处理多个历史RX|按到达epoch推进，不误扣新watchdog|
|错误key、手柄id、接收器地址或旧challenge|拒绝接入，不替换绑定|
|延后保存时Flash失败|保留pending和旧库，不在service里无限重写；显式重试可成功|
|20条绑定已满、添加新id|拒绝保存，不覆盖其他key，不报告已保存|
|20条已满、重配已有id|只更新同id key，其他19条保留，随后能恢复|
|网页保存处于延后阶段|单次B3、等待最终确认，Flash失败/断开如实报告|

双设备掉电发生在持久化/05交界、长时间连续RF丢包、多实体手柄并发负载等仍需实物确认。接收器本地Flash提交不能单独证明手柄的NVM已在掉电前提交。

## 7. F8重连诊断

请求`f8 00`补零，report ID参数0；64字节回复：

|偏移|内容|
|---|---|
|0..3|F8、payload长62、F8版本1、固件修订号4|
|4|已使用绑定数0..20|
|5|其中等于已知bootstrap key的记录数|
|6|当前H=0选择器有效标志|
|7|最近接入结果|
|8..59|下表13个uint32，LE|
|60..63|pending槽mask、待最终key槽mask、已请求保存槽mask、修订号4|

依次计数：`lookup_hits, lookup_misses, restore_requests, restore_accepted, restore_mic_failures, new_pairs, key_updates, commit_requests, commit_deferred, commit_successes, commit_failures, unsaved_disconnects, restore_fallbacks`。

保存请求同时统计本地自动请求和主机B3。结果码：0无；1查询命中；2查询未命中；3新配对关闭；4无绑定；5接入MIC失败；6RF地址不匹配；7手柄id不匹配；8新接入成功；9恢复成功；10导入中；11无空槽。

F0仍为v3，F7的修订号>=4声明F8存在。网页诊断JSON增加`reconnect`，不包含id/key。旧修订号3仍能显示普通F0/F7数据。
