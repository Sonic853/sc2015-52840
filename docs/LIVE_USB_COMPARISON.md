# 本机实物USB对照：原版接收器与XIAO修订号10

更细的分阶段统计、实际突发负载、267次队列满的源码归因及改进优先级见 [USB_DIFFERENCES_AND_QUEUE_REVIEW.md](USB_DIFFERENCES_AND_QUEUE_REVIEW.md)。

后续修订号11的升级、冻结快照与HID负载检查另见 [REV11_LIVE_VALIDATION.md](REV11_LIVE_VALIDATION.md)，本页两份PCAP仍是修订号10的历史观察。

## 结论与范围

2026-11-03在本机分别接入原版与XIAO，使用USBPcap记录启动Steam、连接手柄和左右触控板操作。用户分别报告两轮**连接和触觉均正常**。XIAO声明修订号10；连接恢复后的约89秒抓包段未再出现state1断开事件。

这是短时实物场景与真实USB事务证据，补充此前的软件回归。它不证明所有配对/掉电/多手柄场景、长时间稳定性、每条触觉空口送达或微秒级RF ACK时序。两轮操作轨迹、配对状态和USB拓扑不同，不能直接据USB耗时判断固件性能优劣。

两边均使用`bmRequestType=21`、`SET_REPORT=09`、`wValue=0300`、`wLength=64`，Report ID为0。触觉实测有第8个参数，不能只保留旧7参数示例。原始例：

```text
8f 08 01 15 02 00 00 01 00 00
8f 08 00 64 00 00 00 01 00 00
8f 08 00 00 00 00 00 00 00 02
```

第8参数保留原字节，本报告不凭名称推断全部标志语义。USB成功仅表示主机事务完成，不是每条触觉在RF/执行端完成的证明。

原版STALL completion位于frames3180、3184（83）、3196、3200（AE）、3212（BA），USBD状态`c0000004`；均为短事务，随后重试成功。这为已实现的读取就绪门控提供了实物支持。96参数确为16字节，且随后GET可返回`96 00`；见原版frames3088、3109/3110，支持修订号9对96用途的勘误。

XIAO共32次STALL：26次控制OUT查询SET、6次控制IN GET，分别与采集后FA的`query_busy=26`、`unpublished_gets=6`数量一致；`invalid_sets=0`。TShark独立统计与原始记录解析相符。这些短暂未就绪重试不能等同于此前无效命令的持续拒绝。

原版与XIAO都可在初始无SET的GET里返回先前缓存内容（原版C1/96、XIAO预检留下的FB或零内容）。这不是当前窗口中对应SET一定存在的证明。

## 4. 断开事件的操作背景

### 原版

state事件：frame7连接、3031断开、3161连接、3176连接。用户确认在采集初期手动关开过手柄；恢复后触觉操作阶段没有后续state1事件。不要把这一次手动操作当成原版的无限重连。

### XIAO

观察到如下配对流程：

|frame|相对时间|事实|
|---:|---:|---|
|137|63.923978s|state3，新配对待保存|
|703/707|66.520s附近|两次B3提交|
|705/709|66.520s附近|B1开/关桌面键鼠|
|711→712|66.521689s起|`9f 04 6f 66 66 21`（off!）成功，USB完成耗时84.583ms|
|797|67.119966s|state1断开|
|803/819|67.22s附近|离线状态通知|
|833|69.323961s|state2恢复|
|915起|69.504075s起|持续触觉写入|

用户确认“重新配对过，未手动关机”，并进一步说明关机发生在Steam点击“完成配对”之后。抓包直接记录主机发出了off!，与该操作吻合。因此这里记录为**Steam完成配对流程中的主机关机及随后恢复**，不是用户按键关机，也不计为异常无限重连。USB URB本身不带发起进程PID。FB的1次看门狗断开与此窗口相符；这不能外推成所有看门狗断开都是主机关机，但本次稳定操作阶段没有出现循环。

原版使用已有绑定，XIAO重新配对/换钥/保存并被主机关机，故初始化重试次数与总耗时不能直接一一比较。两次都观察到setting49=2；XIAO还出现过setting48=24，说明操作/配置流并非完全相同的自动回放。

## 5. XIAO采集前后诊断

`live_xiao_before_20261103.json`中无线计数和FB断开计数均为0。采集后、用户退出Steam且保持设备供电时，`live_xiao_after_20261103.json`记录：

- 当前connectedMask=1、watchdog=41、RF队列0，连接仍在线。
- 实际断开：watchdog=1，B2=0、替换=0、换钥加密失败=0、清库=0。
- `ack_deferred=2135`，`stale_session_sets=0`。前者是门控等待期间发反馈ACK的次数，不是发射失败。
- `invalid_sets=0`、USB command drops=0、协议invalid=0、Flash失败=0。
- RX18803、认证18008、重复4751、MIC失败459、协议队列满267。
- 一次新配对、一次换钥、两次提交请求、一次成功保存、一次成功恢复；另有早期8次恢复MIC失败。

这些累计值覆盖XIAO上电至采集后读取的完整区间，**不只覆盖PCAP窗口**。重新配对改变了绑定状态，不能将早期恢复MIC失败直接解释为稳定会话加密错误。

协议队列满267次是仍需保留的真实观察；它可能包含尽力转发失败，但当前计数不标记具体命令，不能将267次全部认定为触觉丢弃。用户体验正常和USB SET成功不能消除这一覆盖缺口。

## 6. 当前裁定

1. 原版实际通信已采集，96语义、读取SET忙重试、触觉64字节USB/8参数格式有直接证据。
2. 修订号10在本次本机短时连接/触觉场景表现正常，抓包稳定段没有无限重连。
3. 先前修订号9故障与这次修订号10测试不是同一环境的严格A/B回放，不能用这两份正常抓包唯一证明某个代码补丁的因果贡献。
4. 长期稳定性、不同USB环境、多手柄负载及队列满的逐命令归因仍未验证。构建脚本中的`hardware_tested=false`表示该构建流程自身未执行硬件测试；本页和带SHA-256的运行记录保存独立实物观察。
